# Identity, Users, Roles, and Permission Overrides — Discovery

**Status:** Read-only architecture audit. No code, migration, route, UI, permission, or role definition was modified to produce this document. Every claim is labelled **CONFIRMED** (I read the cited lines myself this pass), **INFERRED** (a reasonable conclusion from what was read, not stated outright), **PROPOSED** (a recommendation, not existing behaviour), or **UNKNOWN** (not traced this pass). This document builds on, and re-verifies rather than assumes, `ADMINISTRATION_MULTI_ORGANIZATION_DISCOVERY_AND_USE_CASES.md` and `MULTI_ORGANIZATION_ADMINISTRATION_DOMAIN_ARCHITECTURE_STAGE_1.md`.

## 1. Executive Verdict

The backend already models **one identity per user account** with **many-roles-per-account already supported at the schema and resolver level** — `RoleAssignment` is a join table, not a column, and `permissions_for()` unions the permissions of every role a user holds (`app/authorization/model.py:369-374`, `app/authorization/resolver.py:94`, **CONFIRMED**). What does **not** exist anywhere is a per-user *permission* grant layered on top of role permissions: `AccessGrant` is exclusively a camera/site *scope* table (which cameras/sites, not which permissions — `app/users/models.py:135-162`, **CONFIRMED**), and `AccessDecision.permissions` is populated only from `permissions_for(self.roles)` (`app/authorization/model.py:452-453`, **CONFIRMED**) with no second source ever unioned in. So the requested target — `effective_permissions = role_permissions UNION explicit_user_grants` — is **not implemented today**, but the two halves of it (role-permission union, and a per-user grant table pattern) already exist as separate, proven mechanisms that a new `PermissionGrant`-shaped table could follow. There is no role explosion risk in the existing design: roles are a small closed enum with flat, non-inheriting permission sets (`Role`/`Permission`/`ROLE_PERMISSIONS`, `app/authorization/model.py:46-366`, **CONFIRMED**), and the identity layer already anticipates several accounts per role — nothing in `User`/`RoleAssignment` constrains a role to one holder. The single biggest open gap is administrative, not structural: **there is no API to create, update, deactivate, or role-assign a user** — `GET /api/v1/users` is explicitly read-only with `write_available: false` (`app/api/administration.py:382-441`, **CONFIRMED**), and the only account-creation path in the entire codebase is the operator CLI `scripts/manage.py create-user` (**CONFIRMED**). Building "role plus explicit per-user grants" therefore requires: (a) a new table for the grants, (b) extending `decide()`/`AccessDecision` construction to union them in, and (c) — as a genuinely new decision, not inherited from existing code — an anti-escalation rule for who may write to that table, none of which exist today.

## 2. Current Authentication Flow

Traced end to end, `app/auth/service.py` (**CONFIRMED**, full file read):

1. `POST /auth/login` (route not individually re-read this pass, but `AuthService.authenticate` is its handler per the module's own flow diagram, `app/auth/service.py:1-19`) takes `email`+`password`.
2. `AuthService.authenticate` (`service.py:58-80`) loads the user by email (`load_user_by_email`, `service.py:104-119`, eager-loading `role_assignments`, `access_grants`, `organization`), verifies the bcrypt hash, and — deliberately, for timing-attack resistance — verifies against a dummy hash when no user matches (`service.py:39,69-71`) so a missing account costs the same work as a wrong password. Inactive user *or* inactive organization both fail identically (`service.py:76-77`).
3. On success, `decide(user)` (`app/authorization/resolver.py:68-98`) builds an `AccessDecision`: `subject = user.email`, `tenant_id = user.organization_id`, `roles = parse_roles([...RoleAssignment.role])`, `cameras = parse_camera_scope(first AccessGrant)`.
4. `AuthService.issue()` (`service.py:82-95`) mints an access token and a refresh token via `TokenService`, embedding `subject`, `tenant_id`, and `roles` as claims — **not** permissions (`service.py:83-89`, **CONFIRMED**).
5. On every subsequent request, `current_access` (`app/api/dependencies.py:73-95`) verifies the bearer token, then calls `decision_for_claims` (`service.py:122-139`), which **re-loads the user from the database and rebuilds the `AccessDecision` from scratch** — it does not trust the token's role claims as authorization, only as a stale hint compared against the freshly-derived `tenant_id` (`service.py:135-138`, **CONFIRMED**: "Not from the token's own claims... reading roles out of it would mean a revoked role stayed in force until the token expired"). This is the load-bearing design fact for permission-grant revocation (§9): **any DB-level permission change takes effect on the very next request**, with no cache to invalidate.
6. `requires(permission)` (`dependencies.py:98-114`) is the sole per-route authorization gate; it calls `AccessDecision.has()`/`require()` (`app/authorization/model.py:455-463`).
7. **Identity is email, not username.** `User.email` becomes `Principal.subject` at the platform edge and travels no further (`app/users/models.py:71-73`, `app/authorization/model.py:467-476`, **CONFIRMED**).
8. **No external IdP.** No OAuth/OIDC/SAML client code, no `SSO`/`idp`/`saml` identifiers found in `app/auth/*` (**CONFIRMED absence** by direct reading of `app/auth/service.py`, `app/auth/tokens.py`, `app/auth/passwords.py`, `app/auth/cookies.py` — all four files are password/JWT/cookie-shaped only). Authentication is entirely local password-based.
9. Password floor: `hash_password(password, min_length=settings.password_min_length)` (`app/auth/passwords.py:25-42`), enforced at hash time, not stored on the user row — confirms the prior memory note that a 12-char floor is enforced structurally, so a shorter password could never have been set through any code path that calls `hash_password`.

## 3. Current Identity/Account Data Model

`app/users/models.py`, full file read this pass (**CONFIRMED** for every fact below):

- **`Organization`** (`:47-65`) — `id` (str PK), `name`, `slug` (globally unique), `is_active`, `created_at`. One row = one tenant.
- **`User`** (`:68-105`) — `id` (str PK), `organization_id` (FK → `organizations.id`, `CASCADE`, `NOT NULL`), `email`, `display_name`, `password_hash`, `is_active`, `created_at`, `last_login_at`. `UniqueConstraint("organization_id", "email")` — **email is unique per organization, not globally** (`:79-83`, explicit design comment: "the same person may legitimately hold accounts at two customers"). There is **no separate Person/Identity table** — `User` is simultaneously the human identity and the login credential holder; the codebase's own module docstring states this is deliberate ("Four tables, and no more," `:1-18`).
- **`RoleAssignment`** (`:108-132`) — one row per (user, role) pair, `UniqueConstraint("user_id", "role")` — **a user may hold several roles simultaneously today**, each a separate auditable row with `granted_at`/`granted_by`. `role` is stored as free text (the string value of the `Role` enum), not a DB enum, "so that adding a role is a migration of data, not of type definitions across two systems" (`:123-126`).
- **`AccessGrant`** (`:135-162`) — **one row per user** (`UniqueConstraint("user_id")`), holding `camera_breadth` (none/listed/all_in_tenant), `camera_ids`, `site_ids`. This is a **scope** table (which cameras/sites a user can reach), not a permission-grant table. There is no analogous per-user *permission* table anywhere in this file or elsewhere in `app/`.
- **No password reset/invitation/session table** is present in this file (no `PasswordResetToken`, no `Invitation`, no `Session` row — sessions are stateless JWTs per `app/auth/tokens.py`, not re-read line-by-line this pass but consistent with the login flow's issue/verify shape in §2).
- **Lifecycle fields that exist:** `User.is_active` (boolean, hard on/off), `Organization.is_active` (boolean, hard on/off) — both checked at login (`service.py:76-77`) and at `decision_for_claims` (`service.py:131` re-derives from a fresh read, so a deactivation takes effect immediately). **No soft states beyond active/inactive** — no "invited", "suspended-pending-review", "locked" distinct from `is_active`.

## 4. Current Role Architecture

`app/authorization/model.py:46-66` (**CONFIRMED**, full file read):

- Seven roles, a closed Python `enum.Enum`, defined **in code, not the database**: `SUPER_ADMIN`, `ORG_ADMIN`, `RESTAURANT_MANAGER`, `KITCHEN_SUPERVISOR`, `HYGIENE_OFFICER`, `AUDITOR`, `DEVELOPER`. Adding a role requires a code change and deploy, not a DB write.
- Each role is implicitly tenant-scoped: a `RoleAssignment` row belongs to a `User`, and every `User` belongs to exactly one `Organization` (`User.organization_id`, `NOT NULL`, no nullable "platform" sentinel). There is no role or flag anywhere that is *not* tied to a single organization — confirming the prior reports' finding that `super_admin` is not a platform-wide role (§6).
- **One user can hold multiple roles today** — `RoleAssignment` is a table keyed by `(user_id, role)`, and `parse_roles()` (`app/authorization/resolver.py:28-40`) returns a `frozenset[Role]`, and `permissions_for(roles)` (`model.py:369-374`) unions every held role's permissions. This is existing, tested behaviour, not a proposal.
- Roles are **static in code** — `ROLE_PERMISSIONS` is a module-level `dict[Role, frozenset[Permission]]` (`:200-366`), not read from any table. Changing what a role can do requires a code change; nothing in the request path reads permission sets from the database.
- `Role.is_platform_role` (`:63-66`) marks `SUPER_ADMIN` and `DEVELOPER` as able to reach DevTools — this is the only cross-role grouping concept present, and it is still per-tenant (a `super_admin` in Org A cannot reach Org B's DevTools; DevTools routes are gated by `ACCESS_DEVTOOLS` permission which flows through the same tenant-scoped `AccessDecision`).

## 5. Current Permission Architecture

`app/authorization/model.py:69-374` (**CONFIRMED**, full file read):

- `Permission` is a closed, flat `enum.Enum` (~35 values spanning administration, observation surfaces, cameras, incidents, evidence, audit, reporting, product modules, engineering). **No permission inheritance or hierarchy** — the module docstring states this explicitly (`:189-199`): "no inheritance, because an inherited permission is one nobody remembers granting."
- `ROLE_PERMISSIONS: dict[Role, frozenset[Permission]]` (`:200-366`) is the sole source of what a role grants — a static map, hand-curated per role with detailed inline rationale for every inclusion/exclusion (e.g. `KITCHEN_SUPERVISOR` deliberately excludes `VIEW_EVIDENCE` because it's a shared-screen role, `:296-315`).
- `Permission.MANAGE_USERS` and `Permission.VIEW_USERS` already exist (`:83-84`) and are held by `SUPER_ADMIN` (via the `frozenset(Permission) - {MANAGE_PATRON_ID}` blanket grant, `:213`) and `ORG_ADMIN` (explicitly listed, `:217-218`). **`MANAGE_USERS` is declared but has no route that checks it anywhere in the codebase** — re-confirmed this pass: `grep` across `app/api/*.py` for `MANAGE_USERS` finds only its declaration and its inclusion in `ROLE_PERMISSIONS`, never a `Depends(requires(Permission.MANAGE_USERS))` — the only route touching users, `GET /api/v1/users` (`app/api/administration.py:382`), is gated on `VIEW_USERS`, and there is no write route to gate with `MANAGE_USERS` at all.
- **Authorization enforcement chain** (traced, **CONFIRMED**): route → `Depends(requires(Permission.X))` (`app/api/dependencies.py:98-114`) → `current_access` dependency rebuilds `AccessDecision` from the DB every request (`dependencies.py:73-95`, `service.py:122-139`) → `AccessDecision.has()/.require()` checks membership in `self.permissions`, which is populated once in `__post_init__` from `permissions_for(self.roles)` and **never from any other source** (`model.py:442-453`). This is the single choke point — "exactly one code path where a request becomes an identity" per the module's own docstring (`dependencies.py:1-6`).
- **Frontend gating** (`unityworks-vision-ai-frontend/src/app/permissions/`, **CONFIRMED**, both files fully read): `permissions.ts` is a typed mirror of the backend `Permission`/`Role` enums, sourced from `GET /auth/me` at runtime, with an explicit docstring stating it is UX only and not a security boundary (`permissions.ts:1-13`). `guards.tsx` provides `RequireAuth`, `RequirePermission` (route-level, redirect-on-deny), `RequireRole`, and `PermissionGate` (in-page conditional rendering) — none of these enforce anything the backend doesn't independently enforce; every guarded route also re-checks server-side.

## 6. Current Tenant Boundary

- `AccessDecision.tenant_id: str` is a single mandatory field, validated non-empty in `__post_init__` (`app/authorization/model.py:436-451`, **CONFIRMED**) — there is no representation of "more than one tenant" or "no tenant" anywhere in this dataclass.
- The tenant boundary and the identity layer meet at exactly one point: `decide(user)` sets `tenant_id = user.organization_id` (`resolver.py:79-93`) — a `User` row's own FK is the only source of tenant for every request that authenticates as that user. There is no session, claim, header, or request field that can override it (`decision_for_claims` explicitly re-derives `tenant_id` from the DB and rejects a token whose `tenant_id` claim disagrees, `service.py:135-138`).
- **A future per-user permission grant could not accidentally cross an organization boundary through the request path**, because any such grant would necessarily be a row keyed by `user_id`, and `user_id` already implies exactly one `organization_id` via the `User.organization_id` FK (`app/users/models.py:87-89`). The risk is not a query-time leak; it is an **authoring-time** risk — see §10 — of who is permitted to *write* such a grant row, and whether the writer could name a permission that exceeds their own.
- **Scope model precisely:** tenancy is per-`User`, singular, immutable except by editing the `User.organization_id` column directly (no route does this — not even `scripts/manage.py`, which only ever inserts new users into a named `--org`). A single human cannot today hold two accounts that are linked as "the same identity, two tenants" — each account is a fully independent `User` row with its own `id`, `password_hash`, and role assignments (§7).

## 9. Who Can Manage Users — Recommendation

**PROPOSED**, grounded in the existing permission model (§5), not invented: `MANAGE_USERS` (`app/authorization/model.py:83`) already exists, is already held by `SUPER_ADMIN` and `ORG_ADMIN` (`:213,217`), and already has **zero routes to protect** — it is a permission with nothing behind it today. The correct answer is therefore **use the existing `MANAGE_USERS` permission**, not a new one: a future user-management API should gate create/deactivate/role-assign routes on `Permission.MANAGE_USERS`, exactly mirroring how `MANAGE_ORGANIZATION` already gates site/zone writes. This requires no new permission enum value — only new routes consuming a permission that has sat unused since Phase 1. `VIEW_USERS` (already gating the read route) stays the read-side permission, unchanged.

## 10. Permission Delegation / Anti-Escalation

**No mechanism for granting additional permissions exists today** — this section is entirely **PROPOSED** analysis of what a future mechanism must guarantee, since there is nothing to describe as current behaviour beyond the role-grant precedent in §4 (`RoleAssignment.granted_by`, which already records *who* granted a role, `app/users/models.py:130`, **CONFIRMED** — this is the one existing precedent for "delegation is itself an auditable act").

**Concrete anti-escalation rule (PROPOSED):** a grantor may only grant a permission they themselves currently hold in `AccessDecision.permissions` at the moment of granting, checked server-side against the grantor's own freshly-rebuilt `AccessDecision` (not a cached/claimed set) — i.e. `if permission not in grantor_decision.permissions: refuse`. This mirrors the existing `require()` chokepoint (`app/api/dependencies.py:98-114`) exactly: the same function that already answers "can this caller act" is the natural place to also answer "can this caller confer." Concretely this means:

- Holding `MANAGE_USERS` is necessary but **not sufficient** to grant an arbitrary permission — a `MANAGE_USERS`-holding `org_admin` who does not themselves hold `MANAGE_PATRON_ID` (a real, existing exclusion — `ROLE_PERMISSIONS[Role.ORG_ADMIN]` deliberately omits it, `model.py:265-269`) must be structurally unable to grant `MANAGE_PATRON_ID` to anyone, including themselves.
- This rule is enforceable cheaply because `AccessDecision.permissions` is already rebuilt from the DB on every request (§2) — the grantor's current permission set is always fresh at the moment of the write, with no additional caching concern.
- **`super_admin` is the only role today whose blanket grant (`frozenset(Permission) - {MANAGE_PATRON_ID}`) would let it grant almost anything** — this is expected and consistent with it being the most-privileged role in-tenant; the anti-escalation rule still correctly blocks it from ever granting `MANAGE_PATRON_ID` itself, since it doesn't hold that permission either (§5, `model.py:213`). No role today can grant a permission the granting role itself lacks, by construction of this rule.

## 11. Explicit Deny Overrides — Answer and Recommendation

**Answer: no deny-override mechanism exists today**, and I found **no concrete evidence anywhere in the traced code that one is needed**. `AccessDecision.permissions` is a single `frozenset` (`model.py:442`) — additive only, with no complementary "denied" set anywhere in `AccessDecision`, `ROLE_PERMISSIONS`, or `AccessGrant`. The one place the codebase already implements what looks like a "deny" is **not** a deny-override on top of a grant — it's an unconditional refuse at the business-logic layer, independent of any permission: `MANAGE_PATRON_ID`'s write path (`app/domain/patron.require_writable`, per `model.py:172-175`'s comment, not re-read line-by-line this pass but consistent with the comment "the write path refuses until the legal gate is satisfied") refuses **regardless of who holds the permission**, which is a compliance gate, not a per-user deny.

**Recommendation: do not build deny overrides.** `effective_permissions = role_permissions UNION explicit_user_grants` (allow-only composition) is sufficient for every scenario this codebase's own design comments describe, and a deny system would introduce exactly the kind of precedence ambiguity (which wins: a role grant or a user-level deny? a deny on role X but the user also holds role Y?) that the existing flat, non-inheriting `ROLE_PERMISSIONS` design (§5) was explicitly built to avoid ("no inheritance, because an inherited permission is one nobody remembers granting," `model.py:189-199` — the same reasoning applies a fortiori to a deny that silently overrides a grant). If a future need arises to *reduce* what a specific role would otherwise grant a specific user, the correct existing tool is **not assigning that role to that user, or assigning a narrower role plus explicit grants** — never a per-user negative permission.

## 12. User Lifecycle

Current, fully **CONFIRMED**:
- **Created:** only via `scripts/manage.py create-user` (§7) — no product-level event.
- **Activated:** implicitly, at creation (`User.is_active` defaults `True` in the ORM's column default — not explicitly set by the CLI script, meaning it relies on the SQLAlchemy column default, `app/users/models.py:93`).
- **Deactivated:** only via direct DB manipulation or a future `reset_password`-shaped script action — **no CLI subcommand or API route sets `is_active = False`** (`scripts/manage.py`'s subcommands are `list-users`, `create-user`, `reset-password`, `check-password`, `grant`; none toggle `is_active` off; `reset_password` sets it **True**, `scripts/manage.py:152`, **CONFIRMED** — i.e. the only lifecycle-adjacent CLI action *reactivates*, never deactivates).
- **Role-assigned:** `RoleAssignment` rows, created only by `create-user` (one role, at creation) — **no route or CLI subcommand adds/removes a role from an existing user** (**CONFIRMED absence** — `scripts/manage.py`'s subcommand list has no `add-role`/`remove-role`, and no API route touches `RoleAssignment` beyond the read-only join in `GET /api/v1/users`).
- **Password reset:** `scripts/manage.py reset_password` (`:132-160`) — CLI-only, no self-service or API reset flow.
- **Suspended:** not a distinct state from deactivation (§3) — no soft "suspended, pending review" state exists.

## 13. Provisioning Strategy

**PROPOSED**, since §7 found nothing implemented: the smallest change consistent with the existing design (email-uniqueness-per-org, `password_min_length` floor, audit-everything ethos) is an admin-set one-time password issued out-of-band by whoever holds `MANAGE_USERS` in the target organization, mirroring `scripts/manage.py reset_password --generate`'s existing pattern of printing a generated password exactly once (`:156-160`, **CONFIRMED** this pattern already exists for password reset — extending it to account creation is the lowest-novelty option). **No invitation/email delivery mechanism should be assumed or silently designed around** (§7) — if the product needs email-based invitation, that is a new infrastructure dependency requiring its own decision, not a detail to backfill into this document.

## 15. Audit Architecture

`app/domain/audit.py`, full file read this pass (**CONFIRMED**):

- **Existing mechanism:** `AuditTrail` (append-only; explicitly no `update`/`delete` methods, `:172-178`) writes `AuditEvent` rows via `AuditTrail.record(action, organization_id, actor, actor_roles, resource_type, resource_id, outcome, request_id, detail)` (`:185-217`). `AuditAction` is a closed enum (`:36-93`) — "an action that is not here is not audited, deliberately."
- **No user/role/permission-lifecycle actions exist in `AuditAction` today.** The closest existing entries are `LOGIN`/`LOGOUT`/`LOGIN_FAILED` (`:39-41`) and the generic `ADMIN_CHANGED = "admin.changed"` (`:88`) — the latter is undifferentiated and would need to be split, or new enum values added (`user.created`, `user.activated`, `user.suspended`, `role.assigned`, `role.revoked`, `permission.granted`, `permission.revoked`), following exactly the existing pattern of `RESTAURANT_CREATED`/`ZONE_CREATED` (`:90-93`) — **this is a required, additive enum extension for the effective-permission feature, not a parallel audit system.**
- **Structural credential-scrubbing already exists and would apply automatically:** `_scrub()` (`:136-169`) strips any dict key matching `password`, `password_hash`, `token`, `secret`, `credential`, etc. (`_FORBIDDEN_KEYS`, `:103-123`) and pattern-matches JWT/bcrypt/RTSP-credential shapes even under an innocent key name (`_SECRET_SHAPES`, `:126-131`) — so a future `AuditTrail.record(action=AuditAction.PERMISSION_GRANTED, detail={"permission": "manage_cameras", "granted_to": user_id, "granted_by": grantor_id})` would be safe by construction **as long as the caller never puts a password/hash/token into `detail`**, which the existing scrubber already guards against structurally, not by caller discipline alone.
- **Explicit requirement, restated:** never store passwords, hashes, tokens, or secrets in audit rows — already the module's own stated design intent (`:7-12`, "the one caller who forgets writes a credential into the most permanently-retained table in the system") and structurally enforced by `_scrub()`, not merely a convention.
- **Query path is already tenant-scoped** (`AuditTrail.query`, `:219-246`, always filters `AuditEvent.organization_id == organization_id`) — a future permission-grant audit trail inherits this isolation for free by using the same table and the same `organization_id = access.tenant_id` discipline every other write in the codebase already follows.

## 16. Security and Multi-Tenant Risks

1. **Biggest risk: there is no user-management API at all, so every account-lifecycle action today happens outside the authorization model entirely** (§7, §12) — the CLI script has no `Permission` check and no audit write. Building an "explicit permission grant" API on top of a system whose only current provisioning path bypasses authorization and auditing both is the wrong order of operations: **the user/role/permission-write API and its `MANAGE_USERS` gate must exist and be audited before a permission-grant layer is added on top of it**, or the grant layer would be the first-ever audited user-write while account creation itself remains silent and ungated.
2. **Privilege escalation via a future grant table is the second risk**, addressed by the anti-escalation rule in §10 — without it, a `MANAGE_USERS`-holding `org_admin` could grant any permission to any user in their org, including ones the grantor doesn't hold, silently expanding the org's effective privilege ceiling above what any single role was designed to reach.
3. **Self-modification risk:** nothing in `AccessDecision`/`requires()`/`RoleAssignment` today prevents a user from modifying their own roles, because **no write path to `RoleAssignment` exists at all** — the risk is latent, not yet exploitable, but must be closed in the same change that adds the write path (§9's answer applies: gate on `MANAGE_USERS`, and additionally require `grantor.subject != target.email` for any self-referential grant/role write, to close the specific self-escalation case where a `MANAGE_USERS` holder could grant themselves a permission they don't yet hold — reusing the anti-escalation rule of §10 handles this automatically only if it's actually wired to check the grantor's *pre-grant* permission set, not a stale copy).
4. **`AuditEvent.organization_id` has no FK constraint** — carried forward from the prior report (`app/domain/models.py:534` per that report, not re-verified this pass, **INFERRED**) — relevant here because a future permission-grant audit row inherits this same looseness; not a new risk, but worth fixing in the same pass if Organization deletion is ever built (per the prior report's own recommendation).
5. **No rate-limiting or lockout on `scripts/manage.py` password operations was found this pass** (**UNKNOWN** — not searched for; the CLI is a local/shell-access tool, so this is likely out of scope, but flagged since the report explicitly asks about account-created/suspended flows and lockout is adjacent).

## 18. Decisions Required From Product Owner

1. **Where does the permission-grant union happen** — inside `AccessDecision.__post_init__` (grants passed in at construction) or inside `decide()` (grants queried and unioned before constructing `AccessDecision`)? This is an implementation-shape question but has real implications for whether the union can be unit-tested in isolation from a DB session (§9 area — not answered here, flagged for the design phase this document is not part of).
2. **Exact anti-escalation enforcement point and self-grant policy** — confirm the rule proposed in §10 (grantor must currently hold any permission they grant) and confirm whether a grantor may ever grant themselves anything (this document's default is no, per §16.3, but that default needs explicit sign-off since nothing today prevents or permits it — there is simply no code path yet).
3. **New `AuditAction` enum values and exact naming** for account-created/activated/suspended/role-assigned/role-changed/permission-granted/permission-revoked (§15) — the specific string values are a naming decision, not an architectural one, but should be settled before implementation to avoid a later rename of a permanently-retained audit action string.
4. **What the actual account-provisioning mechanism is** for a brand-new organization's first admin (§7, §13) — admin-set one-time password (lowest novelty, extends an existing CLI pattern) vs. email invitation (new infrastructure, not present today) vs. SSO (not present today, no IdP integration exists at all per §2). This is unchanged from both prior reports' open decision #1/#4 and is **not resolved by this document**.
5. **Whether `MANAGE_USERS` alone is sufficient to gate all new user-write routes**, or whether permission-granting specifically should require a *narrower* permission than general user management (e.g. a user with `MANAGE_USERS` could create/deactivate accounts and assign existing roles, but a separate, more tightly held permission would be needed to grant *additional* explicit permissions) — §9 recommends the single existing `MANAGE_USERS` permission for both, but a product owner may reasonably want to split them, since role-assignment and ad-hoc permission-granting are different-shaped risks (a role is a known, reviewed bundle; an explicit grant is arbitrary).
6. **Confirm no deny-override system is wanted** (§11) — this document found no evidence one is needed and recommends against building one; this is presented as a recommendation requiring explicit sign-off, not a decision already made.
7. **Whether `super_admin` should ever become genuinely cross-tenant**, and whether a separate platform-operator concept is wanted instead — **unchanged from the prior reports' open decision**; this document adds no new evidence either way and reaffirms the prior reports' recommendation (§15 of the Stage 1 document) that `super_admin` stay tenant-scoped and any cross-tenant capability be a structurally separate concept that never constructs a multi-tenant `AccessDecision`.
