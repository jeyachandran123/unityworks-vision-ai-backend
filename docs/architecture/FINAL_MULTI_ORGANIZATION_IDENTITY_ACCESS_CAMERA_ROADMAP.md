## 4. Organization lifecycle decision analysis

INFERRED/RECOMMENDED, resolved concretely this pass by tracing the actual insertion point. Today `Organization.is_active` exists as a bare boolean (VERIFIED FROM CODE, Identity §3, `app/users/models.py`) and is checked only at login (`app/auth/service.py:76-77`, cited by Identity §2) and implicitly at `decision_for_claims` (re-derived every request). There is no three-state lifecycle and no cascading behavior today — `Restaurant.is_active` is the existing precedent, and it does **not** cascade to `Zone`/`Camera` (`administration.py:200-239`, cited by Discovery §10.B and Stage 1 §8).

Concrete per-state recommendation, resolved by tracing actual code paths this pass:

- **ACTIVE** — current default behavior, unchanged. Login succeeds, all reads/writes proceed normally, camera streaming and analysis run, reports generate, scheduled/background work runs, evidence is accessible, audit history is written and read normally.
- **SUSPENDED** — RECOMMENDED: insert the check inside `decision_for_claims` (`app/auth/service.py:122-139`), the single choke point identified in §1. On a suspended tenant: login should still succeed (so an admin can review/appeal), all `VIEW_*`-gated reads should continue to work (existing evidence/reports/incidents remain visible), but every `MANAGE_*`/write-gated permission should be refused — this can be implemented as `AccessDecision.permissions` being intersected with a read-only subset before `__post_init__` finishes, when `Organization.status != active`, requiring no change to any of the ~56 existing call sites that check `access.tenant_id`. Camera streaming (live wall) and scheduled analysis work are the one genuinely new decision: RECOMMENDED to also pause these for a suspended org (stop spending compute/storage on a tenant under a billing/incident hold) — this needs an org-status check added to whatever path currently starts a `LiveRuntime`/`VisionRuntime` session (`app/vision/manager.py`, not modified or read in depth this pass per the guardrail against touching runtime code — the insertion point is named, not built). Report generation on existing data should still work (it is a read). Evidence access (read) should still work; evidence writes (new observations arriving) stop naturally once streaming/analysis is paused. Audit history remains fully readable and continues to be written for whatever actions are still permitted (e.g., login, suspension/reactivation events themselves).
- **ARCHIVED** — RECOMMENDED: login refused entirely (mirrors today's `is_active=False` behavior exactly, `service.py:76-77`), all API access refused, camera streaming/analysis fully stopped, no new reports generated, but existing evidence/audit/report data is retained per retention policy and not destroyed — this is a "frozen, not deleted" state, distinct from an eventual Organization-deletion decision (Discovery §18.2 / Stage 1 §23.3, still open, see §25 below).

**Explicitly not resolved here (REQUIRES OWNER DECISION, carried from Stage 1 §22/§23.4):** whether SUSPENDED should cascade to streaming/analysis (RECOMMENDED above, but a real product choice, not free) — today's only precedent (`Restaurant.is_active`) does not cascade, so choosing to cascade at the Organization level is a deliberate divergence that needs explicit sign-off, not an inherited default.

## 10. Feature-level No Access / Read Only / Read+Edit mapping

**New analysis this pass.** The permission enum (35 values, `app/authorization/model.py:69-186`, mirrored exactly in `permissions.ts:15-85`) was inspected feature-by-feature. Verdict: **the mapping is deliberately clean where a feature has a real write action, and deliberately absent (not messy) where it does not** — the codebase's own doc comments state this design intent explicitly at almost every pair.

| Feature area | Read permission | Write permission | Fits No-Access/Read/Read+Edit triad? |
|---|---|---|---|
| Sites, Zones | `VIEW_USERS` gates the read route today (Discovery §5 — an odd but VERIFIED pairing, not `VIEW_CAMERAS`) | `MANAGE_ORGANIZATION` | Yes, cleanly — one read, one write, both exist. |
| Cameras | `VIEW_CAMERAS` | `MANAGE_CAMERAS` | Yes, cleanly. |
| Camera health | `VIEW_CAMERA_HEALTH` | none — health is a runtime signal, not configuration | Fits **No Access/Read Only only** — there is no "edit camera health," by design (Discovery §7, Stage 1 §5g). Do not invent a write permission here. |
| Live feed | `VIEW_LIVE` | none (subscribing is a read-shaped act) | No-Access/Read Only only. |
| Observations | `VIEW_OBSERVATIONS` | none | No-Access/Read Only only. |
| Evidence | `VIEW_EVIDENCE` | `DELETE_EVIDENCE` (destroy, not edit) | **Does not fit Read+Edit** — the only write-shaped action on evidence is deletion, never modification (`Permission.DELETE_EVIDENCE` doc comment, `model.py:102-105`: "Erasing evidence is NOT implied by being allowed to view it"). Model this as No Access / Read Only / Read+Delete, not Read+Edit — inventing an "edit evidence" permission would misrepresent what the system allows to happen to a record that may need to defend a finding. |
| Incidents | `VIEW_INCIDENTS` | `ACKNOWLEDGE_INCIDENTS` and `RESOLVE_INCIDENTS` are two **separate** write actions, deliberately not unified (`model.py:97-100`: acknowledging is "somebody has seen this," resolving "closes a violation," a different judgement) | **Does not fit a single Read+Edit tier** — incidents naturally have three tiers (No Access / Read / Read+Acknowledge / Read+Acknowledge+Resolve), not two. Collapsing acknowledge and resolve into one "Edit" bucket would erase a distinction the permission model was deliberately built to preserve. |
| Reports | `VIEW_REPORTS` | `EXPORT_REPORTS` (take a copy away — not an edit) | **Does not fit Read+Edit** — reports have no edit action at all, ever (they are generated, not authored). Model as No Access / Read Only / Read+Export. Confirms the task's own hypothesis. |
| Users | `VIEW_USERS` | `MANAGE_USERS` (declared, currently unused — §6/§8) | Fits the triad structurally, but the write side is unbuilt — today only No Access / Read Only actually exist in the product; Read+Edit is a declared-but-dormant permission with no route (Identity §5, re-confirmed this pass — grep for `MANAGE_USERS` outside its own declaration/`ROLE_PERMISSIONS` entry returns nothing). |
| Organization | none dedicated — `MANAGE_ORGANIZATION` currently gates Sites/Zones, not an Organization entity itself, since no Organization CRUD exists | same | No triad exists yet — Organization administration is entirely unbuilt product surface (Discovery §5/§10.A). |
| People Count, Demography, Table Occupancy, Cutting Board, Meal Detection | `VIEW_*` for each | `MANAGE_TABLE_OCCUPANCY`, `MANAGE_CUTTING_BOARD` exist; **People Count, Demography, and Meal Detection have no MANAGE permission at all**, by design (`model.py:144-148`: "A MANAGE_* is declared only where there is genuinely configuration to administer... their MANAGE arrives with the configuration model it would protect") | **Inconsistent by design, not by accident** — 2 of 5 modules fit Read+Edit today (Table Occupancy: the floor plan; Cutting Board: the colour policy), 3 do not (nothing to configure yet). Do not add write permissions to the 3 pre-emptively. |
| POS integration | `VIEW_POS_INTEGRATION` | `MANAGE_POS_INTEGRATION` | Fits cleanly. |
| Patron ID | `VIEW_PATRON_ID` | `MANAGE_PATRON_ID` (held by nobody by design pending a DPIA — `model.py:172-175,203-213`) | Fits the triad structurally but is intentionally inert at the write tier — this is a compliance gate, not a gap. |
| Model Evaluation | `VIEW_MODEL_EVALUATION` | none — read-only engineering artifact, explicitly not implied by `VIEW_REPORTS` and deliberately excluded from `ORG_ADMIN` (`model.py:128-134,244-263`) | No-Access/Read Only only, and — critically — **this is an engineering permission, not a business-feature one**, see next row. |
| DevTools / Engineering | `ACCESS_DEVTOOLS`, `REGISTER_DEMAND` | n/a — these are not read/write pairs at all | **Must be a separate axis, never folded into the business-feature triad**, exactly as instructed. `Role.is_platform_role` (`model.py:63-66`) already marks this as a categorically different kind of access ("may reach engineering surfaces"), tenant-scoped identically to everything else but conceptually orthogonal — `VIEW_MODEL_EVALUATION` belongs on this same engineering axis, not the operational one, per its own doc comment above. |

**Summary conclusion:** the permission vocabulary already splits cleanly into read/write pairs for every feature that genuinely has a write action (Sites/Zones, Cameras, POS, Table Occupancy, Cutting Board, Patron ID, Users-when-built). It deliberately has **no** write permission for features that structurally have none (Camera Health, Live, Observations, Model Evaluation) — RECOMMENDED: do not invent one. Two feature areas (Evidence, Incidents) have write-shaped permissions that are **narrower or more granular** than "Edit" — Evidence is Read+Delete, not Read+Edit; Incidents is a three-tier progression, not two. A UI "No Access / Read Only / Read+Edit" selector should be built as a **per-feature configurable set of tiers**, not a single fixed three-state enum applied uniformly — forcing every feature into exactly three tiers would either invent permissions that don't exist (an "edit" on evidence or reports) or collapse real distinctions the backend already enforces (acknowledge vs. resolve). This is a genuine design finding, not a restatement of the prior reports.

### 15.1 The 17-step CCTV/perception recovery validation sequence (procedure document — not executed)

This is a documentation-only procedure for validating that a camera/DVR/perception pathway is healthy end-to-end after any administrative change (retirement, re-enable, credential rotation, host change, zone reassignment) or after a suspected outage. It is written against the entities and boundaries VERIFIED in §1/§14/§15 above and the explicit guardrail that no perception/RTSP/vision_os runtime code was touched, run, or even read in depth to produce it — this is a design-level checklist an operator or a future automated health-check would execute, not a script that was run this pass.

1. **Confirm organizational ownership.** Verify the camera's `organization_id`, `restaurant_id`, and (if set) `zone_id` all resolve to rows within the same tenant, using the same `_restaurant_in_tenant`-style check the create/zone-assignment paths already use (§14). A camera whose parent chain disagrees must fail this step before any further validation proceeds.
2. **Confirm camera registration state.** Read the `Camera` row directly: `camera_key` present and unique within the org, `enabled` and `analysis_enabled` flags explicit (never assume a default), `channel` a valid positive integer.
3. **Confirm RTSP configuration completeness without reading secrets.** Verify `host`, `rtsp_port`, `stream_type`, `username`, and `credential_ref` are all populated (or deliberately blank for a not-yet-wired camera) — never resolve or print the value `credential_ref` points to during this check.
4. **Confirm shared-DVR consistency.** For every other camera sharing this camera's `(host, rtsp_port)`, confirm they all belong to the same `organization_id`/`restaurant_id` — since there is no `dvr_id` FK today (§3, §16), this consistency is the only guard against two organizations' cameras silently sharing a physical unit misconfiguration.
5. **Confirm zone attribution history is intact.** Query `CameraZoneAssignment` for this `camera_key`; confirm exactly one currently-open interval (`effective_to IS NULL`) and that closed intervals never overlap — an overlap or a gap indicates a prior administrative bug, not a perception problem, and must be resolved before continuing.
6. **Confirm the credential reference resolves (existence check only, value never logged).** Using whatever `SecretProvider` mechanism the deployment uses (not independently re-verified this pass — Stage 1 §5e flagged this as UNKNOWN), confirm `credential_ref` resolves to *something* without ever writing that something to a log, response, or audit row.
7. **Confirm network reachability of the host (transport-layer only).** A TCP-level reachability check to `host:rtsp_port`, with no RTSP handshake yet — isolates "is the DVR/camera powered and networked" from "does perception like what it sees."
8. **Attempt RTSP session negotiation.** Full RTSP DESCRIBE/SETUP handshake using the resolved credential; confirm a stream description is returned for the configured `channel`. Failure here means camera/DVR-side misconfiguration (wrong channel, wrong credentials, wrong stream_type), not an application bug.
9. **Confirm frame acquisition.** Confirm at least one frame is actually decoded from the negotiated session within a bounded timeout — a successful RTSP handshake with zero frames delivered is a distinct failure mode from #8 and should be reported as such.
10. **Confirm the frame reaches the acquisition boundary the application owns.** Verify the acquired frame is handed across whatever boundary separates transport from Vision OS (named, not touched, per the guardrail) — this validates the application's own wiring, independent of Vision OS's internal correctness.
11. **Confirm Vision OS reports the camera as covered.** Read camera health/coverage (`VIEW_CAMERA_HEALTH`-gated read, §10) and confirm it reflects "reachable, recently seen" for this `camera_key` — this is the first step that reads a value the application itself computed, not raw transport state.
12. **Confirm analysis is actually running when `analysis_enabled=true`.** Distinct from #8-#11 (streaming can succeed while analysis is off, by design, §15) — confirm a perception cycle is observed to execute against this camera's frames, without inspecting or altering perception internals.
13. **Confirm at least one observation is produced (or correctly produces none).** For a camera newly re-enabled after retirement/outage, confirm the observation pathway is live — either a real observation appears, or the system correctly reports "observed, nothing to report" rather than silence indistinguishable from failure.
14. **Confirm evidence capture, if evidence-triggering conditions are met.** Verify a new `EvidenceRecord` is written under the correct `organization_id`-partitioned storage path (§1/§2) when a condition that should trigger evidence capture is met — validates the evidence pathway specifically, not just observations generally.
15. **Confirm incident generation, if incident-triggering conditions are met.** Verify a new `Incident` row carries the correct `organization_id`, a correctly-populated `restaurant_id`/`zone_id`/`camera_key` snapshot at creation time (§15, `Incident.zone_id`/`restaurant_id` are captured once, not re-derived), and is visible through the normal incident-list read path for the correct tenant only.
16. **Confirm audit trail completeness for every administrative action taken during this validation.** Every state-changing step above (re-enable, credential rotation, zone reassignment if performed as part of recovery) must have produced a corresponding `AuditEvent` (§13) — a recovery procedure that itself goes unaudited defeats the audit model's purpose.
17. **Confirm tenant isolation held throughout.** As the final step, re-run the read paths for incidents/evidence/observations/camera health from a *different* organization's credentials and confirm none of this camera's new data is visible — the recovery is not complete until cross-tenant isolation is positively re-demonstrated, not merely assumed to still hold because it held before the incident that triggered recovery.
