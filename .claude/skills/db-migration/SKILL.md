# Database Migration

## Overview

Tests build the schema with `create_all` and **never run a migration** — except
`tests/app/test_membership_migration.py`. So a migration is unverified by default. Downgrade is not a
rollback plan: it drops columns and partitions, and the `destructive-bash` hook blocks it.

## Writing a revision

```bash
PY=.venv/Scripts/python.exe
$PY -m alembic heads                                   # must be exactly one before you start
$PY -m alembic revision --autogenerate -m "short slug"
```

- The file is named `YYYYMMDD_<rev>_<slug>.py` (`alembic.ini` `file_template`). The URL comes from
  `app/configuration/settings.py`, never `alembic.ini`.
- **Read the autogenerated body.** Autogenerate misses renames (emits drop + add = data loss),
  server defaults, enum value changes and data backfills.
- Use `op.batch_alter_table` for column alters so SQLite works: SQLite rebuilds the table and copies
  every row, which is where data is actually lost. PostgreSQL alters in place.
- Backfills are explicit SQL inside `upgrade()`, idempotent, and never widen access. Mirror
  `20260908_f2a9c4e18b73_organization_memberships.py`: every existing row keeps precisely the access it
  had; a backfilled grant names no grantor.
- Write `downgrade()` honestly, but treat it as documentation, not a recovery path.

## Proving it

A revision that changes authorization, identity, cameras or evidence data needs a test in the shape of
`tests/app/test_membership_migration.py`: upgrade to the previous revision, write live-looking data
through the old schema, upgrade to head, assert nothing about anyone's access changed.

```bash
$PY -m pytest tests/app/test_membership_migration.py tests/app/test_persistence.py
```

For any other revision, at minimum run the whole chain on a disposable SQLite file outside the repo:

```bash
D="$(mktemp -d)"
DATABASE_URL_OVERRIDE="sqlite+aiosqlite:///$(cygpath -m "$D" 2>/dev/null || echo "$D")/check.db" \
    $PY -m alembic upgrade head
rm -rf "$D"
```

`DATABASE_URL_OVERRIDE` is the setting `migrations/env.py` reads through `Settings.database_url`; it
takes precedence over `.env`, so the real database is never touched.

## Applying

```bash
$PY -m alembic current          # against the target DB, with its settings
$PY -m alembic upgrade head
```

Before a production upgrade: a restorable backup exists and has been restored somewhere at least once.

## Observation partitions are files, not tables

`FileObservationLog` partitions are named `<org>_<camera_key>.jsonl` (see
`app/domain/runtime_identity.py`). If runtime identity changes:

```bash
$PY -m scripts.migrate_observation_partitions --dry-run     # default; read every line
$PY -m scripts.migrate_observation_partitions --apply
```

It refuses to overwrite and leaves keys owned by two organizations alone — those need a human
decision, not a script.

## Multiple heads

Two branches each added a revision. Do not delete one. `alembic merge -m "merge heads" <a> <b>`,
read the result, and run the upgrade check above.

## Red flags

- "Autogenerate got it right" without reading it.
- `alembic downgrade` to undo a mistake — write a forward fix.
- A backfill that grants a role, camera or membership the row did not already imply.
- `alembic stamp head` to make an error go away.
